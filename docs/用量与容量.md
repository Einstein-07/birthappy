# BirtHappy 用量与容量说明

> 数据基于 2026-10-31 官方定价页面和本项目当前实现。平台政策可能变化，请以 [Netlify Pricing](https://www.netlify.com/pricing/) 与 [Turso Pricing](https://turso.tech/pricing) 为准。
>
> 下文的 credits 换算是估算，不是 Netlify 的官方账单明细。真实用量以 Netlify 控制台的 Usage 页面为准。

## 1. 先理解 Netlify 的四个计量项

Netlify 免费计划每月有 **300 credits**，它不是“300 次访问”，而是一池共用的额度。

| 项目 | 单价 | 通俗解释 |
| --- | --- | --- |
| 生产部署 | 15 credits / 次 | 每次把新代码发布到正式域名 |
| 带宽 | 20 credits / GB | 浏览器从网站下载的 HTML、JS、CSS、图片等总字节数 |
| Web 请求 | 2 credits / 每 10,000 次 | 每次加载页面、脚本、样式、头像、调用 API 都算请求 |
| 函数计算 | 10 credits / GB-hour | 服务器端渲染页面、运行 API 时占用的内存 × 时间 |

300 credits 如果只用于某一项，大致等于：

| 只用在这一项 | 300 credits 可以换多少 |
| --- | --- |
| 生产部署 | 20 次 |
| 带宽 | 15 GB |
| Web 请求 | 150 万次请求 |
| 函数计算 | 30 GB-hours |

这些项目**共享**同一池额度，不能同时都拿满。例如用了 10 次部署（150 credits），就只剩 150 credits 给带宽、请求和函数计算。

## 2. 一次用户操作大概消耗多少？

下面只计算“点击按钮到接口完成”，**不包含用户打开注册页、首页等页面的静态资源**。真正消耗较大的是页面浏览和部署。

假设：

- Netlify 函数按 1GB 内存计费；
- 一次接口函数执行约 0.2–0.6 秒；
- 普通 API 请求约 2–10KB；
- 头像上传约 100KB。

| 操作 | 请求 | 函数计算 | 带宽 | 约消耗 credits |
| --- | --- | --- | --- | --- |
| 注册账号 | 1 次 | 0.3–0.5s | 几 KB | 约 0.001–0.003 |
| 登录 | 1 次 | 0.2–0.4s | 几 KB | 约 0.001–0.002 |
| 修改资料（不换头像） | 1 次 | 0.2–0.4s | 几 KB | 约 0.001–0.002 |
| 上传并保存头像 | 1 次 | 0.3–0.5s | 上行约 100KB | 约 0.004–0.008 |
| 送一块蛋糕 | 1 次 | 0.1–0.3s | 几 KB | 约 0.001–0.002 |
| 切一次蛋糕 | 1 次 | 0.2–0.8s | 几 KB | 约 0.002–0.005 |
| 打开首页一次 | 10–30 次资源请求 | 0.2–0.5s | 约 250–500KB | 约 0.008–0.02 |
| 打开“我”页一次 | 10–30 次资源请求 | 0.2–0.5s | 约 250–500KB | 约 0.008–0.02 |

结论：

- **注册、登录、点赞、修改资料本身非常便宜。**
- 1,000 次注册的操作消耗大约只有几 credits。
- 一次页面浏览约等于几百次“点按钮”的消耗。
- 真正需要控制的是：**页面流量、头像大小和部署次数**。

## 3. 一个月的实际场景估算

假设：

- 每月 2 次生产部署；
- 每月 10,000 次页面浏览；
- 每次浏览平均 350KB、20 个请求、函数执行 0.3 秒；
- 用户操作：500 次注册/登录、2,000 次送蛋糕、200 次切蛋糕。

| 项目 | 估算 |
| --- | --- |
| 2 次生产部署 | 30 credits |
| 带宽：10,000 × 350KB ≈ 3.5GB | 70 credits |
| 请求：10,000 × 20 = 200,000 次 | 40 credits |
| 函数计算：约 0.83 GB-hour | 8 credits |
| 用户操作 | 通常 < 5 credits |
| **合计** | **约 150 credits** |

在每月 300 credits 的免费额度内，这个规模还有约一半余量。

粗略判断：

- **每月 5,000–15,000 次页面浏览**、少量部署和操作，通常比较安全。
- 接近或超过 20,000 次页面浏览时，就需要看实际 Usage 页面，可能会接近免费上限。
- 头像越大、图片越多，带宽消耗越快。
- 每次部署固定消耗 15 credits，频繁推送代码很容易先耗掉额度。

## 4. 带宽、请求和函数到底是什么

### 带宽

浏览器从 Netlify 下载的数据总量。它包含：

- 首页 HTML；
- JavaScript 和 CSS；
- 头像图片；
- 接口返回的 JSON；
- 页面跳转时加载的数据。

浏览器缓存后，再次访问会减少下载量。头像文件名带版本号，更新后才会重新下载。

### Web 请求

每发出一个 HTTP 请求就算一次，包括：

- 打开一个页面；
- 下载每个 JS、CSS、图标；
- 加载每个头像；
- 点击按钮调用 `/api/...`；
- 页面导航时 Next.js 请求新的页面数据。

一次页面访问不等于一个请求，实际可能是 10–30 个请求。

### 函数计算

Netlify 需要运行你的 Next.js 服务端代码时才会产生：

- 服务端渲染首页、“我”页；
- 注册、登录、送蛋糕、切蛋糕 API；
- 头像接口（如果未命中缓存）。

静态 JS、CSS 文件不需要函数计算。函数计算按“内存 GB × 运行小时”计费，所以一次请求通常只有 **0.000x credits**。

## 5. Turso 免费数据库能存多少？

Turso 免费计划（当前）：

- **5GB 存储**；
- 每月 **5 亿行读取**；
- 每月 **1000 万行写入**；
- 5GB 是累计存储上限，不按月清零；读取/写入额度按月重置。

### 用户容量估算

用户表包含邮箱、UID、密码哈希、称呼、简介、生日、时间戳和头像。没有头像时，一个用户通常约 0.7–1.2KB；头像才是大头。邮箱验证码和注册限流记录是短命数据，验证码 3 天后清理，每天最多新增 100 位注册用户，因此容量可以忽略。

按 5GB 存储、预留 20% 给索引、祝福记录和余量估算：

| 平均头像大小 | 大约可容纳用户数 |
| --- | --- |
| 无头像或 0KB | 百万级（实际还会受读/写额度影响） |
| 40KB | 约 9 万–10 万 |
| 60KB | 约 6 万 |
| 100KB | 约 3.5 万–4 万 |
| 200KB | 约 1.8 万–2 万 |
| 460KB（接近单张上限） | 约 8,000–9,000 |

参考：

- 本项目演示头像约 38–41KB。
- 普通 512×512 JPEG 照片常见在 40–150KB。
- 当前上传逻辑会把图片裁成 512×512 并尽量压到 460KB 以内；不是每张都会接近上限。

对朋友之间的网站来说，100 个用户通常只占几 MB 到几十 MB，远远用不满。

### 祝福记录和修改额度占多少

一条祝福大约几百字节，1 万条祝福通常也只有几 MB。对 5GB 的存储来说，祝福数量一般不是瓶颈，头像才是。

每次资料修改会在 `change_quotas` 留下一条当月记录，每个用户每年最多 12 个月份记录，加上一条生日额度记录，通常不足 1KB/年。修改额度限制的主要作用是防止滥用和刷写，不会对数据库容量或 Netlify 用量造成明显影响。

### 邮箱验证码和每日注册上限

- 验证码只在 10 分钟内有效，最多尝试 5 次；旧验证码会被新验证码作废，超过 3 天的记录会清理。
- 每日注册上限为 100 人（北京时间），同一 IP 哈希最多 5 人；单日验证码邮件全站上限 500 封。
- 即使按每天 100 人、每人 2 封验证码估算，一天也只有约 200 条短记录，占不到 1MB；每天还会清理旧记录。
- 邮件发送通过 Resend HTTP API，主要消耗 Resend 免费额度和 Netlify 函数执行时间（通常 1–3 秒），不占 Turso 存储。
- Resend 免费计划通常为每月 3,000 封、每日 100 封；与每日最多 100 位注册用户的设计基本匹配。实际发送量按“每次点击发送验证码”计数，重发也会消耗额度。
- 如果每天 100 人都注册且每人重发一次，当天可能触及 Resend 每日 100 封上限；需要限制重发或升级 Resend。

## 6. Turso 行读取和行写入怎么理解

Turso 的额度不是按“请求次数”，而是按 SQL 查询实际读取/修改的行数。

| 用户行为 | 大约读取行数 | 大约写入行数 |
| --- | --- | --- |
| 发送验证码 | 3–5（限流计数/插入） | 1–3 |
| 注册 | 3–6 | 4–6（校验、占名额、用户、额度、注册事件） |
| 登录 | 1–2 | 0 |
| 修改 UID（仅一次） | 2–3 | 1 |
| 首页加载 | 当前用户 + 今天生日用户 + 相关祝福 | 0 |
| 送蛋糕 | 2 | 1 |
| 修改资料 | 1 | 1 |
| 切蛋糕 | 待回应祝福数量 | 每个收礼人一条回礼 + 更新祝福 |

首页查询已经增加了按“月-日”的表达式索引，因此不会随着总用户数增长而扫描整张用户表，只会读取今天过生日的人。

粗略判断：

- 每月 5 亿行读取，足够支持非常多的页面访问；
- 每月 1000 万行写入，足够支持大量注册、送蛋糕和切蛋糕；
- 对朋友规模的使用，先成为瓶颈的更可能是 Netlify 带宽/部署额度，而不是 Turso 行数。

## 7. 想扩大容量时怎么办

按优先级：

1. **压缩头像**：把平均头像控制在 40–80KB，用户容量会明显提高。
2. **把头像移到对象存储**：例如 Cloudflare R2、S3，数据库只存 URL。这样 Turso 能存更多用户，但需要额外服务。
3. **减少部署次数**：把修改攒成一次提交，节省 Netlify credits。
4. **升级套餐**：Netlify Personal/Pro、Turso Developer，按实际使用量选择。
5. **更换托管商**：代码可迁移到 Vercel、Cloudflare、Render 或自己的服务器；Turso 数据可继续使用。

## 8. 结论

- 对朋友之间的小规模使用：**当前免费额度很充足，长期运行没有明显技术障碍。**
- 注册、登录、修改、送蛋糕本身非常便宜，不必担心“点一次按钮就花掉很多 credits”。
- 邮箱验证码会让注册流程多出 1–3 次 HTTP 请求和函数执行，但每日 100 人的上限把它限制在很低的量级。
- 真正要注意的是：部署次数、页面带宽和头像大小。
- 5GB 数据库容量在普通头像大小下大约能存数万用户；没有头像时可到百万级。
- “永久免费”没有平台保证，但代码、Turso 数据和本地备份都可迁移，这是比某一家平台更可靠的保障。

建议每月看一次：

```text
Netlify → Project overview / Usage
Turso → Database → Usage
```

把真实用量和本文估算对照，就能知道是否需要优化或升级。
