# BirtHappy 版本规范

> 当前版本：**v2.0.0**  
> 规范：语义化版本 SemVer（`MAJOR.MINOR.PATCH`）  
> 版本号唯一来源：[package.json](../package.json)；页脚自动读取，避免多处手写不一致。

## 1. 版本号格式

```text
MAJOR.MINOR.PATCH
  2  .  0  .  0
```

- **MAJOR（主版本号）**：发生不兼容变更时递增。
- **MINOR（次版本号）**：新增向后兼容功能时递增。
- **PATCH（修订号）**：向后兼容的问题修复、样式/文案修正、安全补丁时递增。
- 预发布版本可使用 `2.1.0-rc.1`，正式发布时去掉后缀。
- 版本号一经发布不覆盖、不复用；有修复就发新版本。

## 2. 何时升哪一位

### MAJOR

- 登录/注册方式发生不兼容变化，例如 v2.0 从账号密码改为邮箱/UID。
- 数据库表结构需要迁移，且旧版本无法直接运行。
- 公开 URL、API 请求/响应格式发生破坏性变化。
- 删除或重命名核心功能。
- 备份格式发生不能向下兼容的变化。

### MINOR

- 新增页面、统计维度、互动方式或账号能力，且旧数据可直接使用。
- 新增可选环境变量；不配置时原有功能仍可运行。
- 新增向后兼容的 API 字段或接口。
- 性能、可访问性或显著体验改进，但不改变既有行为契约。

### PATCH

- 修复 bug、错别字、样式错位、移动端适配。
- 修复安全问题、限流绕过、依赖漏洞。
- 不改变数据结构与 API 契约的文案调整。
- 小幅性能优化。

> 当一次发布同时包含多种变更时，按最高级别递增：例如同时有功能和破坏性改造，发布 MAJOR，且 MINOR/PATCH 归零。

## 3. 发布流程

1. 确认改动范围，判断 MAJOR / MINOR / PATCH。
2. 修改 `package.json` 的 `version`。
3. 更新 `CHANGELOG.md`，写清新增、变更、修复、迁移注意事项。
4. 若涉及数据库，先备份生产库，再在测试库演练迁移/恢复。
5. 在本地执行 `npm run build`，验证核心流程。
6. 提交并打 Git 标签，例如 `git tag v2.0.0`、`git push origin main --tags`。
7. 部署 Netlify，检查页脚版本号、注册、登录、绑定邮箱、注销和首页。
8. 记录部署时间、版本、备份文件与验证结果。

## 4. 数据库迁移规则

- 只做追加式迁移，不在启动时删除用户数据或列。
- 新列优先允许为空或提供默认值；服务端兼容旧数据。
- 先迁移结构，再回填数据，最后建立唯一索引/约束。
- 迁移必须幂等：多次冷启动、多个无服务器实例同时执行都不能破坏数据。
- 破坏性迁移必须先备份，并在维护手册中写明回滚步骤。

## 5. 当前版本说明

`v2.0.0` 是一次 **MAJOR** 更新，原因：

- 注册从账号密码改为邮箱验证码。
- 登录改为邮箱/UID + 密码；旧账号仅保留绑定邮箱前的临时回退。
- 新增 UID、邮箱、验证码、每日注册上限、敏感词过滤、隐私协议、账号注销和页脚注册人数。
- 数据库新增字段与表，旧备份仍需可恢复。

## 6. 与页脚的关系

页脚显示格式：

```text
共 N 位注册用户 · v2.0.0
```

`N` 由数据库实时计数，版本号来自 `package.json`。发布新版本只需要修改 `package.json`，页脚自动更新，不手写第二份版本号。
